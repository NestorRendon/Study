# SQL Database Engines Compared

**Prev:** [[08.3 - SQL Transactions ACID and Isolation Levels]] · **Next:** [[08.5 - SQL Schema Design Normalization and Production Tips]]

---

## Interview one-liner

The biggest split isn't "which SQL database is best" — it's **OLTP vs OLAP**: is this system handling many small, fast transactions (an app's live database), or a few huge analytical queries scanning millions of rows (a reporting warehouse)? That single question determines whether you even want a row-store or a column-store, before any vendor comparison starts.

---

## In plain English

`SELECT` and `JOIN` look the same everywhere, but the engines underneath make very different tradeoffs — some are optimized to handle 10,000 tiny concurrent writes per second (an app's database), others are built to scan a billion rows for one aggregate query and don't care about single-row write latency at all (a data warehouse). Picking the wrong category for the job is a much bigger mistake than picking the "wrong" vendor within the right category.

---

## OLTP vs OLAP — the split that matters most

| | **OLTP** (Online Transaction Processing) | **OLAP** (Online Analytical Processing) |
|---|---------------------------------------------|----------------------------------------------|
| **Storage layout** | **Row-store** — a full row is stored together | **Column-store** — each column stored together |
| **Optimized for** | Many small reads/writes of individual rows | Few, huge aggregate queries scanning many rows but few columns |
| **Real example** | An app's live database: "get this user's profile," "insert this order" | "Total revenue by region, last 3 years" — scans millions of rows but only 2-3 columns |
| **Why the layout matters** | Fetching one full row (all columns) is one disk read | Aggregating one column across millions of rows never has to touch the other unused columns — much less I/O |
| **Examples** | PostgreSQL, MySQL, SQL Server, SQLite | Snowflake, BigQuery, Redshift, ClickHouse |

*This is also the OLTP side of the [[07 Data engineering/Guía Avanzada de Arquitectura de Datos|data platform architecture]] your app's database feeds — see [[Architecture/04 - Data and Analytics Platform Architecture]] for the pipeline that moves data from OLTP into OLAP.*

## OLTP engines compared

| Engine | Type | Standout feature | Watch out for |
|--------|------|----------------------|-------------------|
| **PostgreSQL** | Open source, general-purpose | Extremely feature-rich: JSONB, full-text search, `pgvector` for embeddings ([[06 LLM/08 RAG & Retrieval/04.4 - Vector Database Frameworks Compared]]), extensible | Slightly heavier to tune than MySQL for pure simple-read-heavy workloads |
| **MySQL** | Open source, general-purpose | Extremely widely deployed, simple replication story, fast for simple read-heavy workloads | Historically weaker on complex queries/window functions (much improved in modern versions) |
| **SQL Server** | Microsoft, commercial | Deep integration with the Microsoft/.NET ecosystem, strong tooling (SSMS, SSRS) | Licensing cost, less common outside Windows/enterprise shops |
| **SQLite** | Embedded, serverless (a single file) | Zero setup — the entire database is one file, ships inside the app itself | Not built for concurrent writes at scale — one writer at a time; wrong choice for a multi-user server backend |
| **Oracle DB** | Commercial, enterprise | Extremely mature, heavy enterprise feature set (partitioning, advanced replication) | Licensing cost is significant; mostly seen in large legacy enterprise environments |

---

## OLAP / warehouse engines compared

| Engine | Model | Standout feature |
|--------|-------|-----------------------|
| **Snowflake** | Fully managed, cloud-native | Storage/compute fully separated — scale each independently, pay per query |
| **BigQuery** | Fully managed, serverless (Google Cloud) | No infrastructure to manage at all, pay-per-query-scanned pricing |
| **Redshift** | Managed (AWS) | Deep AWS ecosystem integration, mature |
| **ClickHouse** | Open source, self-hosted or managed | Extremely fast for real-time analytics, popular for event/log analytics at scale |

*Full pipeline context — how raw data gets from an OLTP app database into one of these: [[Architecture/04 - Data and Analytics Platform Architecture]].*

## Decision tree

| If... | Reach for |
|-------|-----------|
| Powering a live application (users read/write individual rows constantly) | An OLTP engine — **PostgreSQL** as the strong general default |
| Need vector search alongside your relational data | **PostgreSQL + pgvector** — one system instead of two |
| Shipping an embedded/local/mobile app with no server | **SQLite** |
| Running company-wide analytics/BI on historical data | An OLAP warehouse — **Snowflake/BigQuery** if you want zero ops, **ClickHouse** if you want raw speed and are willing to self-host |
| Already deep in the Microsoft stack | **SQL Server** |
| Real-time analytics on high-volume event/log data | **ClickHouse** |

## Common traps

| Trap | Why it's wrong | What to say instead |
|------|------------------|----------------------|
| Running heavy analytical queries directly against the production OLTP database | Row-store engines aren't built for scanning millions of rows for one aggregate — it competes with real user traffic for resources | "I'd offload analytics to a warehouse (OLAP), fed by a pipeline, rather than querying prod directly — see [[Architecture/04 - Data and Analytics Platform Architecture]]" |
| Treating "SQL" as one portable language across engines | Core syntax is standardized, but window functions, JSON handling, date functions, and `LIMIT`/`TOP` syntax all vary | "I'd check engine-specific docs before assuming a query is portable" |
| Choosing SQLite for a multi-user web backend | It handles one writer at a time — fine for embedded/local use, a bottleneck for concurrent server writes | "I'd use SQLite only for embedded/local/single-writer scenarios, not a shared server backend" |
| Assuming a managed OLAP warehouse is always cheap | Pay-per-query-scanned pricing (BigQuery) can get expensive fast on unoptimized, unpartitioned tables | "I'd partition/cluster tables and monitor bytes scanned, not just assume managed = cheap" |
