# SQL Schema Design, Normalization and Production Tips

**Prev:** [[08.4 - SQL Database Engines Compared]] · **Next:** [[09 - Spark Essentials]]

---

## Interview one-liner

Normalization removes duplicate data by splitting it across tables — great for write-safety, sometimes bad for read-speed. Knowing when to normalize and when to deliberately break the rule (denormalize) is worth more in an interview than reciting the normal forms from memory.

---

## In plain English

Imagine one big `orders` table with `customer_name`, `customer_email`, and `customer_address` repeated on every single order row for the same customer. Update that customer's address, and you have to update it in a thousand rows — miss one, and now your data disagrees with itself. Normalization is the discipline of storing each fact in exactly **one** place.

---

## Normalization, with a worked example

**Unnormalized** — repeats customer info on every order:

| order_id | customer_name | customer_email | item | amount |
|----------|---------------|-----------------|------|--------|
| 1 | Alice | alice@x.com | Book | 20 |
| 2 | Alice | alice@x.com | Pen | 5 |

| Normal form | Rule | Fixes |
|-----------------|------|-----------|
| **1NF** | Every column holds a single, atomic value — no comma-separated lists in one cell | A `phone_numbers = "555-1234, 555-5678"` column becomes its own table |
| **2NF** | 1NF, plus every non-key column depends on the **whole** primary key, not just part of it (only matters with composite keys) | In an `(order_id, product_id) → product_name` table, `product_name` depends only on `product_id`, not the whole key — move it to a `products` table |
| **3NF** | 2NF, plus no non-key column depends on **another non-key column** (no transitive dependency) | `customer_email` depends on `customer_name`, not on `order_id` directly — move customer info to its own `customers` table |

**After normalizing to 3NF:**

```sql
customers(customer_id, name, email)
orders(order_id, customer_id, item, amount)
```

Now a customer's email is stored exactly once — update it in one place, every order automatically reflects it via the foreign key.

## When to deliberately denormalize

| Situation | Why |
|-----------|-----|
| A read-heavy dashboard needs a join across 5 normalized tables on every page load | Precompute/store a flattened, denormalized version — trade some redundancy for read speed |
| An OLAP/reporting warehouse | Star schemas *deliberately* denormalize (wide fact tables) — see [[08.4 - SQL Database Engines Compared]] — because analytical queries scan, they don't need write-safety the same way |
| Event logs / audit tables | Often intentionally denormalized/append-only — you want the historical snapshot at that moment, not a live-updating join |

**The tradeoff is always the same:** normalized = safer writes, slower/more complex reads. Denormalized = faster reads, risk of the same fact disagreeing with itself across rows if an update misses a spot.

## DDL command cheat sheet

```sql
CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    customer_id INT NOT NULL REFERENCES customers(id),
    amount NUMERIC(10,2) CHECK (amount >= 0),
    created_at TIMESTAMP DEFAULT NOW()
);

ALTER TABLE orders ADD COLUMN status TEXT DEFAULT 'pending';
ALTER TABLE orders ALTER COLUMN status SET NOT NULL;
ALTER TABLE orders DROP COLUMN status;

CREATE INDEX idx_orders_customer_id ON orders(customer_id);

DROP TABLE orders;          -- fails if other tables reference it via FK
DROP TABLE orders CASCADE;  -- also drops dependent objects — dangerous, be deliberate
```

| Constraint | Enforces |
|----------------|-------------|
| `PRIMARY KEY` | Uniqueness + not null, one per table |
| `FOREIGN KEY` / `REFERENCES` | The referenced row must actually exist |
| `UNIQUE` | No duplicate values in this column (can have multiple per table) |
| `NOT NULL` | Column can't be empty |
| `CHECK (...)` | A custom boolean condition must hold for every row |
| `DEFAULT` | Value used when none is provided on insert |

## Production traps beyond the query itself

| Trap | Why it's wrong | Fix |
|------|------------------|-----|
| **N+1 queries** | Fetching a list, then running one separate query per row for related data (e.g. one query per order to get its customer) — 1 query becomes 1 + N | Use a `JOIN`, or batch-fetch with `WHERE id IN (...)` |
| **Missing index on a foreign key** | Joins and cascading deletes on that column force a full scan of the child table — see [[08.2 - SQL Indexes and Query Execution Plans]] | Index every foreign key column, as a default habit |
| **Implicit type conversion** | `WHERE user_id = '42'` on an integer column can silently prevent index use, or in the worst case coerce unexpectedly | Match types explicitly; don't rely on the database to guess |
| **No connection pooling** | Opening a new database connection per request is slow and can exhaust the database's max-connections limit under load | Use a connection pool (e.g. PgBouncer, or your framework's built-in pool) |
| **Long-running migrations locking a live table** | An `ALTER TABLE` that rewrites a huge table can hold a lock for minutes, blocking all reads/writes | Use online-migration tools or additive, backward-compatible migration steps (add nullable column → backfill → make required) |
| **`ON DELETE CASCADE` without thinking it through** | Deleting one row can silently cascade-delete far more data than intended | Be deliberate — `ON DELETE RESTRICT` or `SET NULL` are often safer defaults than `CASCADE` |

## Common traps

| Trap | Why it's wrong | What to say instead |
|------|------------------|----------------------|
| Normalizing everything to 3NF+ by default, everywhere | Read-heavy systems can pay a real join-cost penalty for a write-safety guarantee they don't need as much | "I'd normalize the OLTP write path, and consider denormalized/precomputed views for read-heavy paths" |
| Treating normalization rules as absolute | They're a spectrum of tradeoffs, not a compliance checklist | "I'd normalize until it stops paying off for my actual read/write pattern, and stop there" |
| Fetching related data in a loop | Classic N+1 — invisible in a dev environment with 10 rows, brutal in production with 10,000 | "I'd join or batch-fetch, and watch query counts in profiling, not just query time" |
| Adding `ON DELETE CASCADE` everywhere for convenience | Can silently delete far more than intended when a chain of cascades fires | "I'd default to `RESTRICT`, and use `CASCADE` only where the cascade is genuinely the correct business behavior" |

---

## Interview one-liner (arc close)

> "SQL is declarative — the planner decides *how* to run what I declaratively describe, using indexes and statistics, which is why I always check the execution plan rather than assume performance. Transactions give ACID guarantees, with isolation level as the real tunable knob between correctness and concurrency. Engine choice splits mainly on OLTP vs OLAP — row-store for an app's live writes, column-store for analytical scans — and schema design is a tradeoff between normalized write-safety and denormalized read-speed, not a rule to apply blindly."
