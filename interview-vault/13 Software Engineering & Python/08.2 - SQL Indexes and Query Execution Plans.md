# SQL Indexes and Query Execution Plans

**Prev:** [[08.1 - SQL from Scratch How a Query Executes]] · **Next:** [[08.3 - SQL Transactions ACID and Isolation Levels]]

---

## Interview one-liner

An index trades **write cost and storage** for **read speed** — it's the exact same tradeoff as an ANN index in a vector database ([[06 LLM/08 RAG & Retrieval/04.3 - Vector Index Types and ANN Algorithms]]), just for exact/range lookups instead of nearest-neighbor search. Without one, every query is a full table scan; with the wrong one, it's dead weight slowing down every write.

---

## In plain English

Without an index, finding `WHERE user_id = 42` in a 10-million-row table means checking all 10 million rows — a **full table scan**. An index is a separate, sorted data structure that lets the database jump almost straight to the answer, the same way a book's index lets you skip to a page instead of reading cover to cover.

$$\text{Full table scan} = O(n) \qquad \text{B-Tree index lookup} = O(\log n)$$

At 10 million rows, that's the difference between checking ~10,000,000 rows and checking ~23 — the entire reason indexes matter.

## Index types

| Index type | How it works | Best for |
|------------|-------------------|-----------|
| **B-Tree** (the default almost everywhere) | A balanced, sorted tree — supports equality *and* range queries (`>`, `<`, `BETWEEN`) | The default choice for almost any column you filter or sort by |
| **Hash** | Maps a value directly to its location via a hash function | Pure equality lookups (`=`) only — can't do range queries, rarely worth it over B-Tree in practice |
| **GIN** (Generalized Inverted Index, Postgres) | Maps each element (e.g. each word, each array item) to the rows containing it | Full-text search, JSONB columns, array containment queries |
| **GiST** (Generalized Search Tree, Postgres) | A more flexible tree supporting custom "overlaps/contains" logic | Geospatial data, range types |
| **Bitmap index** | A bitmap per distinct value, combined with fast bitwise AND/OR | Low-cardinality columns (e.g. `status` with 5 possible values) in analytical (OLAP) systems |
| **Composite (multi-column) index** | One index across multiple columns, in a specific order | Queries that filter on several columns together — see column-order trap below |
| **Covering index** | Includes all columns a query needs, so the table itself never has to be touched | Read-heavy queries where avoiding the extra table lookup ("index-only scan") matters |

## Reading a query plan (EXPLAIN)

```sql
EXPLAIN ANALYZE
SELECT * FROM employees WHERE department = 'legal';
```

| Plan node | What it means | Good or bad sign? |
|---------------|-------------------|--------------------|
| **Seq Scan** | Full table scan — every row checked | Fine on a small table; a red flag on a large one with a selective filter |
| **Index Scan** | Uses an index to find matching rows, then fetches each from the table | Good — the common healthy case |
| **Index Only Scan** | The index alone has everything needed — never touches the table | Best case — fastest possible read |
| **Bitmap Heap Scan** | Builds a bitmap of matching rows from an index, then fetches them in physical order | Common and efficient for medium-selectivity filters |
| **Nested Loop** (join) | For each row in table A, scan table B | Fine for small tables; slow if both sides are large and unindexed |
| **Hash Join** | Builds a hash table from one side, probes it with the other | Efficient for larger joins |
| **cost=**, **actual time=** | The planner's *estimate* vs the *real* measured time | A huge gap between estimate and actual usually means stale table statistics |

`EXPLAIN` shows the *plan*; `EXPLAIN ANALYZE` actually **runs** the query and shows real timings — use `ANALYZE` when you need ground truth, but be careful running it on a slow, unbounded, or write query in production.

## When an index is silently NOT used

This is the part that surprises people most — having an index doesn't guarantee it gets used:

| Situation | Why the index gets skipped |
|-----------|----------------------------------|
| `WHERE LOWER(email) = 'x@y.com'` | A function wraps the indexed column — the database would need a **functional index** on `LOWER(email)` specifically, a plain index on `email` won't match |
| `WHERE name LIKE '%smith'` | A **leading wildcard** means the sorted order of the index is useless — it can't jump to "ends with smith." `LIKE 'smith%'` (trailing wildcard) *can* use a B-Tree index |
| Low-selectivity filter (`WHERE is_active = true` when 95% of rows are active) | The planner correctly decides a full scan is *cheaper* than jumping around via an index for that many matches |
| Implicit type mismatch (`WHERE user_id = '42'` when `user_id` is an integer column) | The database may need to cast every row, defeating the index |
| Composite index `(a, b)`, query filters only on `b` | A composite index can only be used left-to-right — filtering on the second column alone generally can't use it |

## Column order in composite indexes

An index on `(department, hire_date)` supports:
- `WHERE department = 'legal'` ✅
- `WHERE department = 'legal' AND hire_date > '2020-01-01'` ✅
- `WHERE hire_date > '2020-01-01'` ❌ (can't skip the leading column)

**Rule of thumb:** put the column used for **equality** filters first, range filters after — and put your most selective/most-frequently-filtered column first.

---

## The tradeoff: why not index everything

| Cost | Why |
|------|-----|
| **Storage** | Each index is a full extra data structure, taking real disk space |
| **Write speed** | Every `INSERT`/`UPDATE`/`DELETE` must also update every index on that table — more indexes = slower writes |
| **Planner overhead** | More indexes means more options for the planner to evaluate, which can (rarely) lead it astray |

---

## Common traps

| Trap | Why it's wrong | What to say instead |
|------|------------------|----------------------|
| "I added an index, so it must be faster now" | Not if the query wraps the column in a function, uses a leading wildcard, or the filter isn't selective enough | "I'd confirm with `EXPLAIN` that the index is actually being used, not just assume it" |
| Indexing every column "just in case" | Slows down every write, and bloats storage, often for indexes that are never used | "I'd index based on actual query patterns — check `WHERE`/`JOIN`/`ORDER BY` columns that are genuinely slow" |
| Missing an index on a foreign key column | Joins and cascading deletes on that column force a full scan of the child table | "Foreign key columns should almost always be indexed" |
| Not re-running `ANALYZE` (statistics refresh) after a large bulk load | The planner's row-count estimates go stale, leading to bad plan choices | "I'd refresh table statistics after major data changes, especially bulk loads" |
