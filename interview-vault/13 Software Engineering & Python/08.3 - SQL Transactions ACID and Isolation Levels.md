# SQL Transactions, ACID and Isolation Levels

**Prev:** [[08.2 - SQL Indexes and Query Execution Plans]] · **Next:** [[08.4 - SQL Database Engines Compared]]

---

## Interview one-liner

A transaction is a promise: **either every statement inside it happens, or none do** — and isolation levels decide how much one transaction is allowed to "see" of another one that's still in progress. Get isolation wrong, and you get bugs that only appear under real concurrent load, never in a single-user test.

---

## In plain English

Imagine transferring money between two bank accounts: subtract from A, add to B. If the server crashes after subtracting but before adding, money just vanished. A **transaction** wraps both statements so the database guarantees they either both commit or both roll back — there's no in-between state anyone can ever see.

---

## ACID, explained with the bank transfer

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 'A';
UPDATE accounts SET balance = balance + 100 WHERE id = 'B';
COMMIT;
```

| Property | What it guarantees | In this example |
|----------|------------------------|----------------------|
| **Atomicity** | All statements in the transaction succeed, or all are rolled back | If the second `UPDATE` fails, the first is undone too — money never just disappears |
| **Consistency** | The database moves from one valid state to another, respecting all constraints | A constraint like `CHECK (balance >= 0)` would abort the whole transaction rather than allow a negative balance |
| **Isolation** | Concurrent transactions don't see each other's uncommitted changes | Another user querying account A's balance mid-transfer doesn't see a half-updated state |
| **Durability** | Once committed, the change survives a crash | After `COMMIT` returns, the transfer is safely on disk, even if the server crashes a second later |

---

## Isolation levels — the part that actually varies

Isolation is the one ACID property with **tunable levels**, because perfect isolation (fully serial execution) is slow — each level trades some correctness guarantees for concurrency/speed.

| Anomaly | What it means |
|-------------|-------------------|
| **Dirty read** | Reading another transaction's **uncommitted** change — which might get rolled back, meaning you read something that "never happened" |
| **Non-repeatable read** | Reading the same row twice in one transaction and getting **different values**, because another transaction committed a change in between |
| **Phantom read** | Re-running the same filtered query twice in one transaction and getting a **different set of rows**, because another transaction inserted/deleted matching rows in between |

| Isolation level | Dirty read | Non-repeatable read | Phantom read | Cost |
|----------------------|:---:|:---:|:---:|------|
| **Read Uncommitted** | ❌ possible | ❌ possible | ❌ possible | Fastest, rarely used in practice |
| **Read Committed** (most databases' default) | ✅ prevented | ❌ possible | ❌ possible | Good default balance |
| **Repeatable Read** | ✅ prevented | ✅ prevented | ❌ possible (varies by engine) | More locking/versioning overhead |
| **Serializable** | ✅ prevented | ✅ prevented | ✅ prevented | Strongest guarantee, most overhead — behaves *as if* transactions ran one at a time |

**Postgres note:** its `Repeatable Read` actually also prevents phantom reads in practice (via MVCC snapshots), stricter than the SQL standard technically requires — a good example of why isolation behavior is engine-specific, not just standard-defined.

---

## How isolation is actually implemented

| Mechanism | Idea |
|-----------|------|
| **Pessimistic locking** | Lock a row before touching it (`SELECT ... FOR UPDATE`); other transactions wanting that row simply wait | Correct but can cause contention/waiting under load |
| **Optimistic concurrency control** | Don't lock — proceed assuming no conflict, then check a version/timestamp column at commit time; if it changed, abort and retry | Better throughput when conflicts are rare, requires retry logic in the application |
| **MVCC (Multi-Version Concurrency Control)** | Keep multiple versions of a row; each transaction sees a consistent snapshot as of when it started, writers don't block readers | What Postgres, MySQL (InnoDB), and most modern databases actually use under the hood |

---

## Deadlocks

Two transactions each hold a lock the other one needs:

```
T1: locks row A, wants row B
T2: locks row B, wants row A
```

Neither can proceed. The database detects this (usually via a wait-for graph) and **kills one transaction** (rolls it back with a deadlock error) so the other can continue.

**How to avoid them:** always acquire locks/update rows in a **consistent order** across your application's code paths (e.g. always update the lower account ID first) — most real deadlocks come from two code paths locking the same two resources in opposite order.

---

## Common traps

| Trap | Why it's wrong | What to say instead |
|------|------------------|----------------------|
| Assuming all databases default to the same isolation level | Postgres/Oracle default to Read Committed; some others differ, and behavior of the same level can vary by engine | "I'd check the specific engine's documented default and behavior, not assume standard SQL guarantees it" |
| Wrapping a read-only report query in a long transaction "just in case" | Long-running transactions can hold back garbage collection (MVCC) or hold locks longer than needed, hurting other transactions | "I'd keep transactions as short as possible, and use read-only mode for pure reporting queries" |
| Thinking Serializable isolation has no cost | It's the strongest guarantee but the most likely to cause contention or forced transaction retries under real concurrent load | "I'd use it only where correctness genuinely requires it, and be ready to handle serialization-failure retries in the app" |
| Retrying a failed transaction without checking *why* it failed | A deadlock or serialization failure should be retried; a constraint violation (e.g. a real duplicate key) will just fail again forever | "I'd only auto-retry on transient concurrency errors, not on data-integrity errors" |
