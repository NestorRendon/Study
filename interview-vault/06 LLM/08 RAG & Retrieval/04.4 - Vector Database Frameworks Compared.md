# Vector Database Frameworks Compared

**Prev:** [[04.3 - Vector Index Types and ANN Algorithms]] · **Next:** [[04.5 - Vector DB Queries Commands and Production Tips]]

---

## Interview one-liner

The real decision usually isn't "which vector DB is best" — it's "do I already have infrastructure this can live inside (pgvector), do I need a dedicated managed service to avoid ops work (Pinecone), or am I at a scale that needs a purpose-built distributed system (Milvus)." Pick based on where you already are, not a leaderboard.

---

## In plain English

Every framework in this note can do the core job — store vectors, run ANN search, return top-K. What actually differs is everything *around* that: do you manage the infrastructure yourself, does it support metadata filtering well, does it do hybrid (keyword + vector) search natively, and how far does it scale.

---

## The main players

| Framework | Type | Index(es) | Metadata filtering | Hybrid search (built-in) | Best for |
|-----------|------|-----------|----------------------------|---------------------------------|-----------|
| **pgvector** | Postgres extension | Flat, IVF, HNSW | ✅ Full SQL `WHERE` — the strongest filtering story of any option here | Via combining with Postgres full-text search (`tsvector`) | You already run Postgres and want one database instead of two — this vault's own xFarm stack uses it |
| **Pinecone** | Managed, cloud-only | Proprietary (HNSW-like) | ✅ Metadata filters | ✅ Sparse-dense hybrid support | Teams that want zero infrastructure ops, willing to pay for a managed service |
| **Weaviate** | Self-hosted or managed | HNSW | ✅ Strong filtering (`where` clauses) | ✅ Native `hybrid()` query (BM25 + vector, fused) | Teams wanting hybrid search out of the box without stitching two systems together |
| **Qdrant** | Self-hosted or managed | HNSW | ✅ Rich filtering, including nested/geo | ✅ Native hybrid via sparse+dense vectors | Performance-focused teams, written in Rust, popular for its filtering + speed |
| **Milvus** | Self-hosted (or Zilliz managed) | Flat, IVF, HNSW, IVFPQ, DiskANN | ✅ Filtering | Partial — via plugins/hybrid modes | Very large scale (billions of vectors), teams with dedicated infra/ops capacity |
| **Chroma** | Embedded / self-hosted | HNSW | ✅ Basic filtering | ❌ (roll your own) | Prototyping, local dev, small-to-medium apps — simplest to get running |
| **Elasticsearch / OpenSearch (kNN)** | Search engine + vector plugin | HNSW | ✅ Full search-engine filtering | ✅ Natively — it's a search engine that *added* vector search, not the reverse | Teams already running Elastic for logs/search who want to add semantic search into the same system |
| **Redis (RediSearch)** | In-memory + vector module | Flat, HNSW | ✅ | Partial | Ultra-low-latency use cases where you already run Redis |

## The decision tree

| If... | Reach for |
|-------|-----------|
| You already run Postgres, and scale is moderate (up to a few million vectors) | **pgvector** — one less system to operate, transactional consistency with your other data |
| You want zero infrastructure to manage, and budget allows a managed service | **Pinecone** |
| You want hybrid (keyword + semantic) search *built in*, not stitched together yourself | **Weaviate** or **Qdrant** |
| You're at true massive scale (100M+ to billions of vectors) and have ops capacity | **Milvus** |
| You're prototyping locally, or building something small/embedded | **Chroma** |
| You already run Elasticsearch/OpenSearch for logs or full-text search | Add its **kNN plugin** instead of introducing a whole new system |
| You need the lowest possible latency and already run Redis | **Redis with RediSearch's vector module** |

## Dimensions that actually matter when comparing

| Dimension | Why it matters |
|-----------|---------------------|
| **Ops burden** | Managed (Pinecone) = no servers to run, but less control and ongoing cost. Self-hosted (Milvus, Qdrant, Weaviate, pgvector) = full control, but you own uptime, scaling, backups |
| **Filtering quality** | A vector search that returns great matches but can't filter by `department = 'legal' AND date > X` forces you to over-fetch and filter in application code — expensive and lossy |
| **Hybrid search support** | Pure vector search misses exact matches (SKUs, legal citations, names) — see [[05 - Retrieval Quality]]. Native hybrid support (Weaviate, Qdrant, Elastic) saves you from wiring BM25 + vector fusion yourself |
| **Consistency model** | pgvector inherits Postgres's ACID transactions — insert a document and its vector atomically. Some dedicated vector DBs are eventually consistent, which matters if your app can't tolerate a brief window where a just-written vector isn't yet searchable |
| **Cost model** | Managed services usually charge per-vector-stored + per-query. Self-hosted shifts cost to infrastructure + engineering time — the real total cost depends on your team's existing ops maturity |

## Common traps

| Trap | Why it's wrong | What to say instead |
|------|------------------|----------------------|
| Picking a vector DB based on a benchmark leaderboard alone | Benchmarks measure raw ANN speed/recall — not filtering quality, ops burden, or how it fits your existing stack | "I'd weigh it against my actual requirements — filtering, consistency, ops capacity — not just recall@k numbers" |
| Adding a dedicated vector DB when you already run Postgres at moderate scale | Extra system to operate, extra data-consistency problem (keeping two databases in sync) for no real benefit at that scale | "I'd start with pgvector and only move to a dedicated system once there's a concrete scale or feature reason" |
| Assuming all vector DBs support the filtering you need | Filter support varies a lot — some only support simple equality, others support full boolean/nested/geo queries | "I'd verify filtering capabilities against my actual query patterns before committing" |
| Ignoring hybrid search support when keyword-precision matters (SKUs, IDs, names) | Pure vector search silently returns semantically-similar-but-wrong results for exact-match-sensitive queries | "I'd check whether the framework does hybrid search natively, or plan to stitch BM25 in myself" |
