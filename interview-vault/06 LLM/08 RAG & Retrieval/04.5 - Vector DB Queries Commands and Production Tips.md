## Interview one-liner

Every vector DB exposes the same four operations — **upsert, query, filter, delete** — under different syntax. What actually separates a toy demo from a production system is everything around those four calls: pre- vs post-filtering, hybrid fusion, multi-tenancy, and batching — this note is the cheat sheet for both.

---

## The four core operations, side by side

### 1. Create the index / collection

```sql
-- pgvector
CREATE TABLE document_chunks (
    id BIGSERIAL PRIMARY KEY,
    content TEXT,
    department TEXT,
    embedding VECTOR(1536)
);
CREATE INDEX ON document_chunks
    USING hnsw (embedding vector_cosine_ops);
```

```python
# Pinecone
pc.create_index(
    name="docs", dimension=1536, metric="cosine",
    spec=ServerlessSpec(cloud="aws", region="us-east-1")
)

# Qdrant
client.create_collection(
    collection_name="docs",
    vectors_config=VectorParams(size=1536, distance=Distance.COSINE)
)

# Chroma
collection = chroma_client.create_collection(name="docs")
```

### 2. Upsert (insert or update)

```sql
-- pgvector
INSERT INTO document_chunks (content, department, embedding)
VALUES ('...text...', 'legal', '[0.01, -0.02, ...]');
```

```python
# Pinecone
index.upsert(vectors=[
    {"id": "chunk_1", "values": embedding, "metadata": {"department": "legal"}}
])

# Qdrant
client.upsert(collection_name="docs", points=[
    PointStruct(id=1, vector=embedding, payload={"department": "legal"})
])

# Chroma
collection.add(ids=["chunk_1"], embeddings=[embedding],
                metadatas=[{"department": "legal"}], documents=["...text..."])
```

### 3. Query top-K, with a metadata filter

```sql
-- pgvector
SELECT id, content, embedding <=> :query_embedding AS distance
FROM document_chunks
WHERE department = 'legal'
ORDER BY distance
LIMIT 10;
```

```python
# Pinecone
index.query(vector=query_embedding, top_k=10,
            filter={"department": {"$eq": "legal"}})

# Qdrant
client.search(collection_name="docs", query_vector=query_embedding,
               query_filter=Filter(must=[FieldCondition(key="department",
                                    match=MatchValue(value="legal"))]),
               limit=10)

# Chroma
collection.query(query_embeddings=[query_embedding], n_results=10,
                  where={"department": "legal"})
```

### 4. Delete / update

```sql
-- pgvector
DELETE FROM document_chunks WHERE id = 42;
```

```python
# Pinecone
index.delete(ids=["chunk_1"])

# Qdrant
client.delete(collection_name="docs", points_selector=[1])
```

## Pre-filtering vs post-filtering — the trap that silently kills recall

When you combine a metadata filter with a vector search, **where** the filter is applied matters enormously:

| Approach | How it works | Problem |
|----------|-------------------|------------|
| **Post-filtering** | Run ANN search for top-K first, *then* drop results that fail the filter | If the filter is selective (e.g. only 2% of docs match `department = 'legal'`), you can easily end up with **zero** results after filtering, even though matching documents exist — they just weren't in the unfiltered top-K |
| **Pre-filtering** | Apply the filter *before* or *during* the ANN search, so the index only considers already-eligible candidates | The correct behavior for selective filters — but not every index/framework supports this efficiently (it can degrade back toward brute-force within the filtered subset) |

**Check which one your framework does by default.** pgvector, Qdrant, and Weaviate support genuine pre-filtering; some simpler setups only do post-filtering, which quietly breaks the moment your filters get selective.

## Hybrid search: combining keyword (BM25) and vector search

Pure vector search misses exact-match cases (SKUs, IDs, legal citations); pure keyword search misses paraphrases. Hybrid search runs both and **fuses** the rankings, usually with **Reciprocal Rank Fusion (RRF)**:

$$\text{RRF score}(d) = \sum_{\text{ranker} \in \{\text{BM25}, \text{vector}\}} \frac{1}{k + \text{rank}_{\text{ranker}}(d)}$$

where $k$ is a small constant (commonly 60) that dampens the influence of any single very-high rank. A document ranked #1 by BM25 but not retrieved by vector search at all still gets a meaningful score — it doesn't need to appear in both lists to matter.

| Framework | Hybrid support |
|-----------|---------------------|
| **Weaviate** | Native `hybrid()` query, `alpha` param tunes the BM25/vector balance |
| **Qdrant** | Native, via sparse + dense vectors combined |
| **Elasticsearch/OpenSearch** | Native — it's a search engine with vector search added |
| **pgvector** | Manual — combine a `tsvector` full-text query with a vector query yourself, fuse in application code |
| **Pinecone** | Supports sparse-dense hybrid vectors directly in the same query |

## Multi-tenancy and namespaces

Serving multiple customers/tenants from one vector DB needs isolation so Tenant A's query can never surface Tenant B's data — a real security requirement, not just an organizational nicety.

| Pattern | How | Tradeoff |
|---------|-----|-----------|
| **Namespaces / collections per tenant** | Pinecone namespaces, separate Qdrant/Weaviate collections | Strong isolation, but doesn't scale well to tens of thousands of tenants (index overhead per collection) |
| **Metadata filter per tenant** (single shared index) | Every query always includes `WHERE tenant_id = X` | Scales to many tenants easily — but a missing/buggy filter is a real data-leak risk, so this must be enforced at the query-building layer, never left to the caller |

## Scaling and batching tips

| Tip | Why |
|-----|-----|
| **Batch upserts** (hundreds to thousands at once), don't insert one vector at a time | Network round-trip overhead dominates single-vector upserts; batching is often 10-100x faster |
| **Rebuild vs incrementally update** | Most modern indexes (HNSW, IVF) support incremental inserts — full rebuilds should be rare, planned events, not routine |
| **Shard by tenant or time** at very large scale | Keeps individual indexes smaller and queries faster; also makes deleting old data (e.g. a time-partitioned shard) cheap |
| **Warm the index / cache after deploy** | A freshly started service can have cold caches — the first queries after a restart may be noticeably slower until the working set is warm |
| **Monitor recall in production, not just at index-build time** | Recall can silently drift as data grows and search-time parameters (`ef_search`, `nprobe`) stay fixed — periodically re-benchmark against a brute-force sample |

## Common traps

| Trap | Why it's wrong | What to say instead |
|------|------------------|----------------------|
| Getting zero results after adding a metadata filter | Classic post-filtering problem — the filter is applied *after* top-K, and none of the top-K happened to match | "I'd confirm the framework does pre-filtering, or increase `top_k` before filtering to compensate" |
| Inserting vectors one at a time in a loop | Massive unnecessary network overhead | "I'd batch upserts — most SDKs accept a list of vectors in one call" |
| Relying on the caller to always pass the right tenant filter | One missing filter in one code path is a data leak across tenants | "I'd enforce tenant scoping centrally — e.g. in a query-building layer everyone goes through — not trust every call site to remember it" |
| Never re-checking recall after the dataset has grown 100x | Search-time parameters tuned for a small index may badly under-serve a much larger one | "I'd periodically re-benchmark recall against a brute-force ground truth as the collection grows" |
| Building hybrid search by just concatenating two result lists | Two unrelated score scales (BM25 scores vs cosine similarity) aren't comparable — naive concatenation over- or under-weights one source | "I'd use rank-based fusion (RRF) instead of comparing raw scores directly" |

---

## Interview one-liner (chapter close)

> "A vector DB's core job is ANN search over embeddings — everything else is production engineering around that: pick the right similarity metric for the embedding model, pick an index (HNSW by default, IVFPQ at billion-scale), pick a framework based on ops burden and filtering needs rather than a leaderboard, and get pre-filtering and hybrid fusion right, because both fail silently rather than loudly."
