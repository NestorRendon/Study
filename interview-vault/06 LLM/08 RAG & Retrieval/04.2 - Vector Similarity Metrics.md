# Vector Similarity Metrics

**Prev:** [[04.1 - Vector Databases from Scratch]] · **Next:** [[04.3 - Vector Index Types and ANN Algorithms]]

---

## Interview one-liner

"Closest" only means something once you pick a distance function. **Cosine** compares direction (meaning) and ignores magnitude; **dot product** rewards magnitude too (fast, but needs normalized vectors to behave like cosine); **Euclidean** compares straight-line distance and is the natural fit outside of text embeddings.

---

## In plain English

A vector is just a list of numbers — comparing two of them for "closeness" isn't one obvious operation, it's a *choice*, and different choices genuinely produce different rankings. Getting this wrong is subtle: your search still returns *something*, it just quietly returns the wrong things, ranked in the wrong order.

*The mathematical derivations (why cosine ≈ Pearson correlation, geometric intuition) live in [[03 Mathematics/02 - Similarity Correlation and Convolution]]. This note is the vector-DB-flavored cheat sheet: which metric, when, and how each framework asks you to specify it.*

---

## Notation

| Symbol | Meaning |
|--------|---------|
| $\mathbf{q}, \mathbf{d}$ | Query vector, document/chunk vector |
| $\|\mathbf{q}\|$ | Euclidean norm (length) of $\mathbf{q}$ |
| $n$ | Number of dimensions in the vector |

---

## The four metrics

$$\text{Cosine similarity} = \frac{\mathbf{q} \cdot \mathbf{d}}{\|\mathbf{q}\| \, \|\mathbf{d}\|} \qquad \text{Cosine distance} = 1 - \text{Cosine similarity}$$

$$\text{Dot product (inner product)} = \mathbf{q} \cdot \mathbf{d} = \sum_{i=1}^n q_i d_i$$

$$\text{Euclidean (L2) distance} = \|\mathbf{q} - \mathbf{d}\|_2 = \sqrt{\sum_{i=1}^n (q_i - d_i)^2}$$

$$\text{Manhattan (L1) distance} = \|\mathbf{q} - \mathbf{d}\|_1 = \sum_{i=1}^n |q_i - d_i|$$

---

## What each one actually captures

| Metric | Compares | Sensitive to magnitude? | Range | Real intuition |
|--------|----------|--------------------------------|-------|-------------------|
| **Cosine similarity** | Only the *angle* / direction between vectors | No — a vector scaled 10x has identical cosine similarity | $-1$ to $1$ (usually $0$ to $1$ for text embeddings) | "Do these two chunks talk about the same thing," regardless of how long or emphatic either text was |
| **Dot product** | Angle **and** magnitude | Yes | Unbounded | Rewards vectors that are both *aligned* and *large* — used when the model's own training objective was dot-product-based (common in modern embedding models) |
| **Euclidean (L2)** | Straight-line distance in space | Yes | $0$ (identical) upward | The natural "physical distance" metric — dominant outside NLP (image embeddings, sensor data, geospatial) |
| **Manhattan (L1)** | Sum of per-dimension differences | Yes | $0$ upward | Less sensitive to one dimension being a huge outlier than L2 (no squaring); less common for embeddings, more for tabular/robust use cases |

---

## The fact that trips almost everyone up: cosine vs dot product

If every vector is **L2-normalized** (scaled to length 1) before storing, then:

$$\text{Cosine similarity}(\mathbf{q}, \mathbf{d}) = \mathbf{q} \cdot \mathbf{d} \quad \text{(when } \|\mathbf{q}\| = \|\mathbf{d}\| = 1\text{)}$$

Dot product becomes **mathematically identical** to cosine similarity once vectors are normalized — and dot product is cheaper to compute (no division, no square roots). This is exactly why many vector DBs default to, or strongly recommend, dot product: it's cosine similarity's fast path, not a different metric, *as long as you remember to normalize*. Forget to normalize, and dot-product search silently starts favoring longer/larger-magnitude vectors — a real, hard-to-notice bug.

---

## How to choose

| Situation | Use |
|-----------|-----|
| Text embeddings (OpenAI, Cohere, sentence-transformers) | **Cosine** (or normalized dot product — same result, faster) |
| Embedding model's own docs say it was trained with a specific metric | **Match that metric exactly** — some models (e.g. certain retrieval-tuned models) are only calibrated for dot product or L2 |
| Image embeddings, geospatial data, sensor readings | **Euclidean (L2)** — magnitude is often meaningful here |
| Long-tail/outlier-heavy numeric features (not typical for embeddings) | **Manhattan (L1)** — more robust to one dimension dominating |
| Binary/hashed vectors | **Hamming distance** (count of differing bits) — a different family entirely, used with LSH-style indexes |

## How each framework asks you to specify it

| Framework | Syntax / parameter |
|-----------|-------------------------|
| **pgvector (Postgres)** | Operators: `<=>` cosine distance, `<->` L2 distance, `<#>` negative inner product |
| **Pinecone** | `metric` param at index creation: `"cosine"`, `"dotproduct"`, `"euclidean"` |
| **Weaviate** | `distance` in the class schema: `cosine`, `dot`, `l2-squared`, `manhattan`, `hamming` |
| **Qdrant** | `distance` in collection config: `Cosine`, `Dot`, `Euclid` |
| **Milvus** | `metric_type`: `COSINE`, `IP` (inner product), `L2` |

**pgvector example**, ranking by cosine distance (smaller = more similar):

```sql
SELECT id, content, embedding <=> query_embedding AS distance
FROM document_chunks
ORDER BY distance
LIMIT 10;
```

---

## Common traps

| Trap | Why it's wrong | What to say instead |
|------|------------------|----------------------|
| Mixing normalized and unnormalized vectors in the same index | Dot product results become incomparable — some scores dominated by magnitude, others not | "I'd normalize consistently at write time, every time, or use cosine directly instead of relying on dot product" |
| Using L2 distance for text embeddings without checking the model's training metric | Some embedding models aren't well-calibrated for L2 — rankings can look plausible but be subtly worse than the model's intended metric | "I'd check the embedding model's documentation for its intended similarity metric before picking the index's distance function" |
| Treating similarity **score** as a probability or confidence | Cosine similarity of 0.82 isn't "82% confident" — it has no such calibrated meaning | "I'd use similarity scores for *ranking*, not as a calibrated confidence number" |
| Forgetting distance and similarity are inverses | Sorting cosine *distance* ascending is correct; sorting cosine *similarity* ascending gets you the worst matches first | "I'd double check whether the framework returns a distance (lower = better) or similarity (higher = better)" |
